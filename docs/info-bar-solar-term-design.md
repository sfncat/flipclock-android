# 信息栏优化与节气/三伏/九九显示方案

> 修订版 v3（2026-09-07）：对齐代码现状，补充生肖、第二排字体、节气+期段同日显示、冷启动布局修复等迭代。
> 本方案的两条硬约束：**字体尽量大**、**防烧屏全程各信息层不重叠**（见 §2）。

## 1. 背景与问题

### 1.1 当前架构（与代码现状对齐）

- 信息栏（`info_bar.c/h`）：横屏为顶部单行/双行横条；竖屏为左侧单列/双列（`info_vertical` 默认开启，传统竖排：CJK 直立、ASCII 旋转 90°、≤4 个连续 ASCII 整体横排）。文本生成集中在 `flipclock_info_bar_refresh()`。
- 天气已并入信息栏，**不是独立绘制**：
  - 横屏天气一律并入顶部日期栏（`weather_merge_landscape` 固定 `true`，无设置开关）；
  - `date_on_top_portrait`（竖屏日期置顶横排，信息栏含天气在左下，默认 `true`）；
  - 独立 `weather_overlay.c` 仅在 `weather_large_three_bars`（固定 `false`，无设置开关）时绘制。
- 防烧屏：`BURN_IN_PERIOD_MS=60000`（60s 正弦波），信息栏偏移 `+value`、时间卡片偏移 `-value`，`value = 屏短边 × burn_in_protection_offset × sin(phase)`，`offset` 配置范围 0–5%（典型 1.5%）。
- 农历：`lunar.c` 离线算法（1900–2100），输出如 `丙午马年 七月初一`（干支年含生肖）。
- 节气/三伏/九九：`solar_terms.c` 离线算法（1900–2100），与 `test/almanac/almanac_ref.py` 逐天对拍一致。

### 1.2 问题一：信息栏字体太小

- 横屏单行要容纳 日期+星期+农历+天气 四段，总宽受限，字号被迫缩小。
- 竖屏单列（含竖排）同样面临 农历+节气+期段 叠加后的高度/宽度约束。
- 结论：内容多时，单行/单列排版是字体大小的主要瓶颈。

### 1.3 问题二：防烧屏移动时重叠

- 信息栏与卡片反向移动，极端相位（各到 ±振幅）时两者间距最小。
- 天气层并入信息栏后，独立天气层重叠问题已消除；剩余风险集中在**双行/双列信息栏自身变高/变宽后与卡片的安全距离**（见 §4.4、§5 核算）。

## 2. 核心设计原则

| # | 原则 | 约束口径 |
|---|------|----------|
| P1 | **字体尽量大** | 任何模式下字号 = 可用空间的**双向自适应**最大值（内容过宽缩小、过窄放大，目标占满约 92% 可用宽/高），下限 8px。双行/双列的动机是给每段内容更大的宽度预算，从而**放大**字号。 |
| P2 | **防烧屏全程各层不重叠** | 布局核算以**极端相位**为基准：信息栏与卡片反向各移动一个振幅 `amp`，任意时刻间隙 ≥ 2·amp。见 §4.4 公式。 |
| P3 | **无内容回退单行** | 当天无节气/三伏/九九时保持现有单行/单列布局与字号，不牺牲日常观感。布局预留始终按双行/双列（`two_line_info` 开启时），避免冷启动首帧尺寸错误。 |

---

## 3. 设计方案

### 3.1 核心思路：双层/双列布局

当 `two_line_info` 开启时，信息栏始终按双层（横屏）或双列（竖屏）预留尺寸；当天有节气/三伏/九九内容时实际绘制两行/两列，无内容时回退单行/单列（字号基准用半高，避免过大）。

```
横屏（two_line，有节气内容）：
┌─────────────────────────────────────────┐
│  2026-09-07  星期一  晴 28°              │  ← 第1行：日期 + 星期 + 天气
│  丙午马年 七月廿六  白露                  │  ← 第2行：农历 + 节气/三伏/九九
└─────────────────────────────────────────┘

横屏（two_line，无节气内容）：
┌─────────────────────────────────────────┐
│  2026-09-07  星期一                     │  ← 第1行：日期 + 星期
│  丙午马年 七月廿六  晴 28°               │  ← 第2行：农历 + 天气（天气下移）
└─────────────────────────────────────────┘

竖屏（dual_column，沿用竖排规则）：
┌──────┬──────┬──────────────────────────┐
│ 丙午  │ 星期  │                          │
│ 马年  │ 一    │    时间卡片               │
│      │      │                          │
│ 七月  │ 晴   │                          │
│ 廿六  │ 28°  │                          │
│      │      │                          │
│ 白露  │      │                          │
├──────┴──────┤                          │
│ （左列=农历+节气，右列=星期+天气）        │
└─────────────┴──────────────────────────┘
```

> 示例日期均经 `test/almanac/almanac_ref.py` 验证：2026-09-07 = 丙午马年 七月廿六 = 白露。

### 3.2 节气/三伏/九九内容规则

| 当天情况 | 显示内容 | 示例 |
|----------|----------|------|
| 是节气日 | 节气名（2 字） | `白露`、`秋分` |
| 三伏期内（非节气日） | `初伏/中伏/末伏` + 第X天 | `初伏第二天`、`中伏第二十天` |
| 九九期内（非节气日） | `一九~九九` + 第X天 | `一九第一天`、`九九第九天` |
| 节气 + 期段同日 | **两者都显示**，空格分隔 | `大暑 初伏第九天`、`冬至 一九第一天` |
| 无特殊内容 | 不显示 | 保持单行/单列 |

口径约定（与 `test/almanac/` 参考实现一致）：

- **入伏当天 = 初伏第一天，冬至当天 = 一九第一天**（天数从 1 起算）。
- 三伏落在 7 月中旬 ~ 8 月下旬，九九落在 12 月中旬 ~ 次年 3 月上旬，**时间上不重叠**，共用同一文本位。
- 中伏可能 10 或 20 天（随立秋早晚），期段文本最长 `中伏第二十天`（6 字）。
- 节气名只显示在节气当天（一年 24 天）。
- 节气与三伏/九九同日时两者都显示（如 2026-07-23 大暑恰逢初伏第九天），文本最长约 10 字（节气 2 + 空格 + 期段 6~7）。

### 3.3 显示逻辑

```
if (two_line_info 开启) {
    布局始终按双行/双列预留（横屏 2.0× 高、竖屏 1.8× 宽）
    if (solar_term_text 非空) → 实际绘制两行/两列
    else → 回退单行/单列（字号基准用半高）
} else {
    保持现有单行/单列布局
}
```

> **冷启动修复**：布局预留不依赖运行时 `solar_term_text`（该字段在 refresh 时填充，晚于首次 layout）。若按内容判断预留，冷启动首帧 rect 仍是单行尺寸，双行绘制字极小。`two_line_info` 开启即按双行/双列预留，转屏/重启后尺寸一致。

`solar_term_text` 由 `flipclock_info_bar_refresh()` 生成（与日期/星期/农历同处，按 `tm_yday` 缓存），内容为 §3.2 表格的显示文本。

## 4. 技术实现

### 4.1 数据结构扩展

#### `info_bar.h` 新增字段

```c
struct flipclock_info_bar {
    // ... 现有字段 ...

    bool two_line;                    // 双行/双列模式激活
    TTF_Font *font_line[2];           // 每行/列独立字体对象（字号可能不同）
    int  font_px_line[2];             // 每行/列当前字号
    char solar_term_text[INFO_TEXT_LENGTH];  // 节气/三伏/九九文本（refresh 填充）
};
```

字体管理约定：

- 双行/双列两区**独立测量、独立字号**（内容长度差异大，独立自适应才能做到 P1）。
- 两行字号不同 → 需要 2 个 `TTF_Font*`；字号不变时**复用**对象，仅当字号变化才 `TTF_CloseFont` + `TTF_OpenFont`。
- **第二排字体**：idx=1（横屏第二行 / 竖屏右列）使用 `weather_font_path`（设置界面"第二排字体"），idx=0 使用 `info_bar_font_path`（"信息栏字体"）。未设置第二排字体时回退信息栏字体。

#### `flipclock.h` 新增配置

```c
struct flipclock {
    // ... 现有字段 ...

    bool two_line_info;   // 双行/双列信息栏开关（默认 true）
    char almanac_today[32]; // 伪造"今天"调试键（yyyy-MM-dd，默认空 = 用真实日期）
};
```

### 4.2 节气/三伏/九九算法（完整）

#### 4.2.1 接口（`solar_terms.h`）

```c
#ifndef __SOLAR_TERMS_H__
#define __SOLAR_TERMS_H__

#include <stddef.h>

/* 该日恰为节气时返回节气名（如"白露"），否则 NULL。表外年份返回 NULL。 */
const char *solar_term_of(int year, int month, int day);

/* 该日在三伏或九九期内时返回期段文本（如"中伏第二十天"、"一九第一天"），
   否则 NULL。三伏与九九时间不重叠，三伏优先判断。 */
const char *solar_period_of(int year, int month, int day);

/* 信息栏显示文本：节气与期段同日则都显示（空格分隔），否则显示非空者；均无则空串。 */
void solar_term_text_for(int year, int month, int day,
                         char *buf, size_t buf_size);

#endif
```

#### 4.2.2 节气查找表

- 表范围 **1900–2100 共 201 年**，每年 24 个节气（年内日号）：

```c
/* 序与 test/almanac/almanac_ref.py TERMS 一致：0=小寒 … 23=冬至。
   数据由 test/almanac/terms_1900_2100.txt 经 gen_c_table.py 生成，勿手改。 */
static const uint8_t SOLAR_TERMS_TABLE[201][24] = { ... };
```

- 存储 201×24 = 4824 字节。
- 查表：`i = (month-1)*2`，命中 `SOLAR_TERMS_TABLE[year-1900][i] == day` → 节气 `TERMS[i]`；`i+1` 同理（中气）。

#### 4.2.3 三伏算法

```
庚日判定：儒略日数 jdn % 10 == 7（天干为"庚"）
初伏起点 = 夏至后第 3 个庚日 = 夏至后首个庚日 + 20 天，持续 10 天
中伏起点 = 夏至后第 4 个庚日 = 初伏起点 + 10 天，长度 = 末伏起点 - 中伏起点（10 或 20 天）
末伏起点 = 立秋后第 1 个庚日，持续 10 天
期段文本：第 n 天 = 名称 + "第" + 汉字天数 + "天"（1..20）
```

#### 4.2.4 九九算法

```
冬至日（当年 12 月用当年冬至；1–3 月用上一年冬至）
offset = 目标日 - 冬至日（天数）
0 ≤ offset ≤ 80 → 第 (offset/9 + 1) 个九 第 (offset%9 + 1) 天，如 offset=0 → "一九第一天"
offset ≥ 81 或 < 0 → 不在九九期
```

#### 4.2.5 生肖（农历年份）

- `lunar.c` 新增 `ZODIAC[12]`（子鼠丑牛寅虎卯兔辰龙巳蛇午马未羊申猴酉鸡戌狗亥猪），与地支同索引。
- 干支年格式从 `丙午年` 改为 `丙午马年`。
- `gz_index = (lunar_year - 4) % 60`，生肖 = `ZODIAC[gz_index % 12]`。

#### 4.2.6 优先级与边界

- 节气与三伏/九九同日时**两者都显示**（§3.2）。
- 三伏与九九不重叠，`solar_period_of` 先判三伏即可。
- 表外年份（<1900 或 >2100）：全部返回空，信息栏回退单行，不报错。
- 时区：按北京时间（UTC+8）日历日。

### 4.3 渲染流程

#### 横屏双层绘制（`_draw_horizontal_two_line`）

```
1. 第1行文本 = date + weekday + (有节气内容时 weather)
   第2行文本 = lunar + solar_term_text + (无节气内容时 weather)
   （空段跳过，分隔符仅在相邻非空段间；星期始终在天气之前）
2. 对每行（独立处理，独立字号，独立字体）：
   a. line_h = (rect.h - gap) / 2，gap = rect.h * 0.08（两行间距）
   b. 基础字号 base_px = line_h * 0.85 * info_scale
   c. 双向自适应：测量行宽，超出 rect.w*0.92 则缩小；不足 rect.w*0.85 且字号 < line_h*1.1 则放大
   d. idx=1（第二行）用第二排字体（weather_font_path），idx=0 用信息栏字体
   e. 第1行居中于上半区，第2行居中于下半区（中间留 gap）
```

#### 竖屏双列绘制（`_draw_vertical_two_column`）

```
1. 左列 = lunar + solar_term_text；右列 = weekday + weather（空段跳过）
2. 两列均沿用传统竖排渲染：
   - CJK 直立；ASCII 旋转 90°；≤4 个连续 ASCII（如温度"28"）整体横排不旋转
   - 各列独立字号自适应
3. 左列用信息栏字体，右列用第二排字体（weather_font_path）
4. info_vertical=false 时回退横向堆叠
```

### 4.4 防重叠机制（公式化）

符号：`amp` = 防烧屏振幅（像素）= 屏短边 × `burn_in_protection_offset`；信息栏偏移 `+`、卡片偏移 `−`。

| 场景 | 安全条件（极端相位） |
|------|----------------------|
| 横屏双层：信息栏底 vs 卡片顶 | 初始间隙 `g ≥ 2*amp` |
| 竖屏双列：信息栏右 vs 卡片左 | 初始间隙 `g ≥ 2*amp` |
| 行/列内部 | 每行严格限 line_h 内、每列限 rect.w/2 内绘制，字号自适应保证不越界 |
| 天气层 | 已并入信息栏，无独立天气层 |

## 5. 布局影响核算

### 5.1 横屏双层

- `info_h = h * INFO_RATIO`（0.10），双层时 `info_h' = 2.0 * info_h`（每行与单行等高，避免双行字号反而比单行小）。
- 两行间距 `gap = rect.h * 0.08`，每行有效高 `line_h = (rect.h - gap) / 2`。
- 卡片代价：`reserved_top` 增大，`card_size` 约 −9%（可接受）。
- 防烧屏：间隙 `g ≥ 2*amp` 自动满足（卡片下移）。

### 5.2 竖屏双列

- `info_w = w * INFO_RATIO_PORTRAIT`（0.22）+ 2*space_size，双列时 `info_w' = 1.8 * info_w`。
- 卡片代价：`min_width` 约 −25%，卡片过窄时收窄列宽兜底。
- 防烧屏：竖屏 X 向移动，`g ≥ 2*amp` 需成立。

### 5.3 日期归属

- `date_on_top_portrait=true`（默认）：日期在顶部横条，双列左/右列不含日期。
- `date_on_top_portrait=false`：日期在信息栏内，双列时日期并入左列。
- 横屏双层时日期始终在第 1 行。

## 8. 字号自适应算法

### 8.1 算法（双向）

```
输入：文本内容、基础字号 base_px、最大宽度 max_w（= rect.w*0.92）
1. 用 TTF_SizeUTF8 测量文本宽度 w
2. 若 w > max_w → 缩小：new_px = base_px * (max_w / w)，下限 8px
3. 若 w < max_w*0.85 且 px < 行高上限 → 放大：new_px = base_px * (max_w*0.92 / w)，上限行高*1.1
4. 迭代上限 12 轮
```

### 8.2 字体尽量大的机制

1. **内容分流**：双行/双列把长内容拆到两个区，每区宽度预算翻倍。
2. **独立自适应**：两区独立测宽、独立取字号。
3. **横屏 2.0× 预留**：双行每行与单行等高，避免双行字号比单行小。
4. **顶部日期字号放宽**：竖屏顶部日期条 max_h 0.90、safety w/80、target_w 0.97。

### 8.3 字体对象缓存

- 字号不变时复用 `TTF_Font*`；仅字号变化才重开。
- `font_line[2]` 各自维护 `font_px_line[i]`。
- 第二排字体（idx=1）与信息栏字体（idx=0）独立缓存，切换字体时重开。

## 10. 风险与注意事项

1. **节气表正确性**：4824 个日期，错一位即界面错误。由表原稿 + 双源对拍 + 五道回归兜底；内置表禁止手改。
2. **节气+期段同日文本长度**：最长约 10 字，横屏第二行字号自适应会缩小，属预期行为。
3. **第二排字体**：切换后需重启应用生效；未设置时回退信息栏字体。
4. **布局跳变**：有/无节气内容时单/双行切换，字号会跳变（P3 固有代价）。
5. **冷启动**：布局预留不依赖 solar_term_text，避免首帧尺寸错误（已修复）。
6. **防烧屏**：任何 offset 配置（0–5%）下不得重叠。
7. **时区**：节气按北京时间日历日；设备时区非 UTC+8 时可能差一天。
